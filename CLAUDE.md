# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project

jamail is a terminal email client built with ratatui/crossterm. It connects to IMAP servers, caches all mail locally in a compressed SQLite database, and provides instant full-text search via FTS5.

It also has optional CalDAV calendar sync, with its own terminal UI, and a standalone CalDAV *server* daemon. It ships as **four binaries** sharing one library crate (`src/lib.rs`):

- **`jamaild`** (`src/bin/jamaild.rs` + `src/daemon.rs`) — a background daemon. Owns every configured account's IMAP connection/sync loop (plus, for any account with `caldav` configured, a CalDAV calendar sync loop — see `src/calsync.rs`) and all writes to the local cache, and is the sole place that decides to fire a desktop mail notification — and, since the alarm clock moved here, the calendar alarm popups too (`calnotify::run_alarm_loop`, one thread over every caldav account's cached events). Optionally also runs a real inbound CalDAV HTTP server (`daemon.caldav_server_listen`, off by default) exposing those same accounts' calendars to other CalDAV clients — see `src/caldav_server.rs`. Suitable for `systemd --user` (`contrib/systemd/jamaild.service`); syncs every account continuously from startup regardless of whether any client is connected. Takes two setup subcommands besides the default `serve`: `jamaild google-auth <account>` (the one human-in-a-browser step of Google Calendar OAuth — see `src/goauth.rs`) and `jamaild caldav-check [<account>]` (resolve an account's CalDAV credentials the way the sync thread does and list what discovery finds); neither touches a running daemon.
- **`jamail`** (`src/bin/jamail.rs`) — the terminal UI for mail. Reads the cache directly and talks to `jamaild` over the IPC protocol in `src/ipc.rs` for anything needing a live IMAP session (which folder to IDLE on, mark-seen, Sent/Draft uploads) and for the sync-event stream. Auto-spawns a `jamaild` if none is reachable.
- **`jacal`** (`src/bin/jacal.rs` + `src/calapp.rs`) — a separate terminal UI for calendars: year/month/week/3-day/day/single-event views rendered as colored table grids (recurring events expanded to every occurrence in range, all-day events shown across every day they span), with the day-column views drawn against a shared time grid when the terminal has room (Week view stacks Saturday and Sunday in one last column); create/edit/delete, manual sync trigger. Alarm notifications are `jamaild`'s job, not jacal's. Reads calendar data from the same local cache and talks to `jamaild` over the same IPC protocol to trigger a sync and queue event create/update/delete requests, mirroring how `jamail` queues Sent/Draft uploads. Only shows accounts with `caldav` configured; exits immediately with a clear message if none are. Auto-spawns a `jamaild` if none is reachable, same as `jamail`. See `src/calendar.rs`, `src/caldav.rs`, `src/calsync.rs`, and `src/calnotify.rs` module docs for the iCalendar parser/serializer, CalDAV client, daemon-side sync loop, and alarm notification scheduling, respectively — and their doc comments for explicit, deliberate scope limitations (editing/deleting a recurring event always acts on its master `VEVENT`, IANA-timezone-only, etc).
- **`jadav`** (`src/bin/jadav.rs` + `src/jadav/`) — a standalone, self-hosted CalDAV server daemon meant to run on a *server* host (behind a TLS-terminating reverse proxy), not next to the TUIs: it owns many calendars for one principal, speaks the full RFC 4791/4918/6578 surface stock clients (iOS, DAVx5, Thunderbird, `jamaild`) probe, and has its own SQLite store (`jadav.db`, see `src/jadav/store.rs`) — it never touches `mail.db` and has no IPC socket. It mirrors selected calendars two-way with Google (REST) and other CalDAV servers (`jadav/mirror.rs`, `jadav/google.rs`, `jadav/caldav_remote.rs`) and is a real RFC 6638 scheduling server: client writes run through the pure iTIP broker (`jadav/itip.rs`) and the resulting invitations/RSVPs/cancellations leave as iMIP mail through the operator's own SMTP server, while inbound iMIP mail is read from the operator's own IMAP account and applied to the calendar whose identity was addressed (`jadav/imip.rs`). Config lives in a `jadav:` section that may be the *only* thing in its config file (`jadav --config <path>`, else `$JAMAIL_CONFIG`, else the default path). Deployment artifacts: `contrib/docker/Dockerfile.jadav`, `contrib/docker/jadav.compose.yml`, `contrib/systemd/jadav.service`.

Config is read from `~/.config/jamail/config.yaml` (or `$JAMAIL_CONFIG`) by **all four** binaries independently (each reads what it needs; only `jamaild` needs IMAP/CalDAV credentials, only `jamail` needs SMTP credentials for compose/send, only `jacal` needs `caldav` configured on at least one account). Database lives at `~/.local/share/jamail/mail.db`, opened independently by the three mail/calendar-client binaries — `jadav` has its own store (SQLite WAL mode allows concurrent reads/writes from multiple connections, same as before the daemon split).

Rust edition 2024 — uses let-chain syntax (`if let ... && let ...`).

## Build Commands

```bash
cargo build --bins       # compile jamail, jamaild, jacal, and jadav
cargo run --bin jadav -- --config ./jadav.yaml check-config   # validate a jadav config; `serve` runs the CalDAV server
cargo run --bin jamail   # run the mail TUI (needs IMAP config and a TTY; auto-spawns jamaild)
cargo run --bin jacal    # run the calendar TUI (needs a caldav-configured account and a TTY; auto-spawns jamaild)
cargo run --bin jamaild  # run the daemon in the foreground (needs IMAP config, no TTY needed)
cargo clippy --all-targets -- -D warnings   # lint (lib + all four bins + tests/)
cargo fmt                # format
```

Unit tests live inline in each module under `#[cfg(test)]` (`cargo test`). They cover pure logic (config parsing, folder ordering, notification triggers, draft raw-message building, status-label text, iCalendar parsing/serialization in `src/calendar.rs`, calendar view navigation/form validation in `src/calapp.rs`, alarm scheduling in `src/calnotify.rs`), IPC framing/serialization/version-handshake/reconnect behavior (`src/ipc.rs`), daemon request-handling/client-broadcast/notification-dispatch/socket-lifecycle behavior over real `UnixStream` pairs (`src/daemon.rs`), CalDAV discovery/sync/CRUD/conflict behavior over a real local mock HTTP server (`src/caldav.rs`, `src/httpc.rs`), Google OAuth token refresh/caching/`invalid_grant` behavior over the same kind of mock endpoint plus the PKCE URL/redirect parsing and the `0600` refresh-token file (`src/goauth.rs`), CalDAV auth-scheme resolution (`src/calsync.rs`), inbound CalDAV server discovery/auth/CRUD/REPORT behavior over a real local `TcpListener`, including round-trips through this crate's own `caldav.rs` client (`src/caldav_server.rs`), and DB/App state transitions via `MailDb::open_in_memory()` and a `test_app()` helper — not TUI rendering. `tests/smoke.rs` is a real end-to-end integration test: it spawns the actual compiled `jamaild`/`jamail` binaries and talks to the daemon over a real Unix socket (see that file's module doc for exactly what it covers and the one deliberate scope limitation — no live IMAP/TLS server is faked, since doing so would require weakening certificate validation in production code; the same limitation applies to `jacal`/CalDAV, verified instead by manual smoke runs against a real `jamaild` plus the local mock-HTTP-server tests in `src/caldav.rs`).

## Architecture

### Daemon/Client IPC (jamaild <-> jamail)

Replaces the old single-process "background sync thread" model. Full protocol
definition — framing, versioning, error semantics, socket path resolution,
lifecycle/shutdown — is documented in `src/ipc.rs`'s module doc comment;
daemon-side process/connection model is documented in `src/daemon.rs`'s. Summary:

- **Transport**: a Unix domain stream socket, `$XDG_RUNTIME_DIR/jamail/jamaild.sock`
  by default (overridable via `JAMAIL_SOCKET` env var or `daemon.socket_path` in
  config), directory `0700` / socket `0600`.
- **Framing**: `[u32 LE length][JSON payload]`, capped at `ipc::MAX_FRAME_BYTES`.
- **Handshake**: client sends `ClientHello{protocol_version}`; daemon replies
  `ServerHello::Ok` or `ServerHello::VersionMismatch` (then closes) — see
  `ipc::PROTOCOL_VERSION`/`ipc::is_compatible`.
- **Requests** (`jamail` -> `jamaild`, one `Response` each): `Ping`,
  `SetCurrentFolder{account,folder}` (IDLE-target hint only — never starts/stops
  syncing an account), `MarkSeen`, `SetFlagged{account,folder,uid,flagged}` (star/unstar — jamail's `*`), `EnqueueUpload` (base64'd raw message; result
  arrives later as an `UploadComplete`/`UploadError` event, correlated by
  `local_id`), `ForceReconnect`, `SyncNow{account}` (full pass now — jamail's `u`), `Shutdown` (graceful: sets every account's
  `sync::SyncControl.shutdown`, unlinks the socket, exits — same path SIGTERM/SIGINT
  trigger).
- **Events** (`jamaild` -> `jamail`, unsolicited, tagged with `account`): the wire
  form of `sync::SyncEvent`, produced by `ipc::wire_event`.
- **Client reconnect**: `ipc::IpcClient` owns a persistent connection with
  automatic reconnect/backoff, surfaced to the UI as `ClientEvent::{Connected,
  Disconnected, Fatal}` — `Fatal` (version mismatch) stops retrying; anything else
  keeps retrying indefinitely, mirroring the old sync thread's own 5s-backoff
  reconnect style.
- **Notification ownership**: `daemon::dispatch_sync_event` runs inside `jamaild`'s
  per-account event-pump thread and is the *only* place that decides to call
  `notify::notify_new_mail` — `jamail` never references the `notify` module at all
  (enforced by a test in `tests/smoke.rs`).

### Threading Model

**Inside `jamaild`**: one `sync::spawn_sync_thread` (unchanged from before the
daemon split) plus one "event pump" thread per configured account (the pump reads
that account's `SyncEvent`s, calls `daemon::dispatch_sync_event` for notification
delivery, then broadcasts the tagged event to every connected client). Each accepted
client connection gets a reader thread (`daemon::handle_client` — handshake +
request loop) and a writer thread (drains a per-client channel fed by both direct
responses and broadcast events, so only one thread ever writes to a given socket).

**Inside `jamail`**: the TUI event loop (unchanged in shape from before the daemon
split) polls keyboard/mouse events with a 200ms timeout and drains
`ipc::IpcClient::event_rx` via non-blocking `try_recv()` instead of an in-process
`mpsc::Receiver<SyncEvent>`. Reads from the database directly for email content, same
as always.

### Multi-Account & Multi-Folder

- Multiple IMAP accounts are configured in `config.yaml` (IndexMap preserves order)
- Each account can optionally filter/order folders via a `folders` list in config
- `jamaild` builds one `SyncControl` (Arc) per configured account at startup and never tears any of them down while running — this is what lets every account keep syncing, and notifications keep firing, regardless of which one (if any) a connected `jamail` is currently looking at:
  - `current_folder: RwLock<String>` — which folder to IDLE on (updated by `ipc::Request::SetCurrentFolder`, no thread restart needed)
  - `shutdown: AtomicBool` — signal to stop (set by `daemon::Daemon::trigger_graceful_shutdown` on `ipc::Request::Shutdown`/SIGTERM/SIGINT)
  - `folder_filter: RwLock<Vec<String>>` — which folders to sync
- "Switching accounts" in `jamail` is client-side only now: no thread spawn/teardown, just load the new account+folder from the local cache and send `SetCurrentFolder` so `jamaild` knows which one to prioritize for IDLE
- Folder switching within the same account works the same way — loads cached emails, sends `SetCurrentFolder`

### Module Responsibilities

- **lib.rs** — Declares every shared module as `pub mod`; both binaries depend on this one library crate
- **bin/jamail.rs** — The terminal client's `main`/event loop: terminal setup/teardown, event loop dispatch, folder/account navigation (now just a local cache load + an `ipc::Request::SetCurrentFolder`, no thread management), compose key dispatch, SMTP send handler, mouse text extraction, clipboard copy, daemon auto-spawn on startup
- **bin/jamaild.rs** — The daemon's `main`: argument dispatch over `daemon::run()` (the default) plus the two setup commands `google-auth` (PKCE flow via `goauth::authorize_interactive`, refresh token written `0600` to `<data dir>/jamail/oauth/<account>.token`, or printed with `--print`) and `caldav-check` (`calsync::connect` + `discover_calendars`, printing each calendar and flagging the ones a `caldav.calendars` filter excludes)
- **daemon.rs** — Daemon process/connection model: spawns one `sync::SyncControl`+sync thread+event-pump thread per configured account at startup (never torn down while running), accepts IPC client connections (`handle_client`: handshake, request loop, per-client writer thread, broadcast registration), `dispatch_sync_event` (the notification-ownership decision), socket bind/stale-socket recovery (`bind_or_recover`), SIGTERM/SIGINT + `Request::Shutdown` graceful-shutdown handling
- **ipc.rs** — The `jamaild`<->`jamail` wire protocol: versioned framing (`write_frame`/`read_frame`), `Request`/`Response`/`Event`/`ClientHello`/`ServerHello` message types, socket path resolution (`resolve_socket_path`, env var > config > XDG default), the client-side `IpcClient` connection manager (auto-reconnect with backoff, `Connected`/`Disconnected`/`Fatal` lifecycle events)
- **app.rs** — All UI state and rendering (ViewMode::FolderSelect/List/Detail/Search/Compose), folder tree, vertical folder label, mouse selection tracking, compose view (body editor, autocomplete, file browser)
- **mail.rs** — IMAP protocol: connect (implicit-TLS connections are built by hand — bounded `connect_timeout`, TCP keepalive 30 s/10 s/3 via `socket2`, a `SESSION_READ_TIMEOUT` of 5 min on the socket, and a `try_clone`d handle kept as `MailClient.raw`; `abort_handle()` hands out a `ConnectionAbort` that `shutdown`s the shared socket from another thread, and `wait_for_changes` re-applies the read timeout the `imap` crate clears after each IDLE round so the `DONE` reply read is bounded too — a laptop that suspends or switches networks leaves the socket locally "established" while the peer is gone, and without all this the sync thread blocked in a read forever), list_folders, sync_folder (incremental via UIDVALIDITY), sync_flags (refreshes `\Seen` for every cached message of the folder and **prunes the ones the server no longer has there** — a `UID FETCH … FLAGS` answers only for existing UIDs, so a silent UID was moved or expunged by another client; `db::delete_emails_by_uid` drops it with its FTS row and attachments), MIME parsing, IMAP IDLE, date parsing, HTML→text conversion (via w3m subprocess). `FolderInfo` also derives `Serialize`/`Deserialize` — it's reused verbatim as the wire type in `ipc::Event::FoldersLoaded`
- **db.rs** — SQLite schema (v9: account+folder scoped mail tables unchanged since v4 — plus, in v8, `idx_emails_list`, a covering index for the folder list queries (`get_email_list`/`get_global_inbox`/`search_emails` select exactly its columns), because `emails` rows carry the compressed bodies and listing a 20k-message folder used to read every row's page, and in v9 `emails.is_flagged` (IMAP `\Flagged`, the star; `set_flagged` flips one row locally, `update_flags` takes `(uid, is_unread, is_flagged)` from the server) with the index rebuilt to cover it; `calendars`/`calendar_events` added in v5; `calendar_sync_log` added in v6; `calendars.identity` in v7 — the address the CalDAV server attached to a calendar, jadav's `owner-identity`, which `jacal` writes as `ORGANIZER` for events created there; an append-only change log the inbound CalDAV server's RFC 6578 `sync-collection` support reads to answer "what changed since token X"; `local_messages` tracks draft/sending/send_error/sent status plus independent upload_status/upload_error for remote Sent/Draft folder uploads), zstd compression/decompression, FTS5 search, schema migration, CRUD operations, known-address extraction for autocomplete. `get_email_account_uid_and_folder()` returns the owning account alongside uid/folder — needed since `jamaild` now syncs every account concurrently, so routing a mark-seen request by account (not just assuming "the current one") matters, notably from the cross-account Global Inbox view. **The v4->v5, v5->v6, v6->v7, v7->v8 and v8->v9 upgrades are additive** (`migrate_v4_to_v5_add_calendar_tables`, `migrate_v5_to_v6_add_sync_log`, `migrate_v6_to_v7_add_calendar_identity` — the last checks `PRAGMA table_info` first, since the shared calendar DDL already carries the column): each only adds its new tables/columns and never drops/recreates existing ones, unlike every schema bump before v5 — picking up calendar support must not cost an existing install its cached mail (or, later, its already-synced calendar data). `calendar_events.local_status` (`CAL_STATUS_SYNCED`/`PENDING_CREATE`/`PENDING_UPDATE`/`PENDING_DELETE`/`CONFLICT`) mirrors `local_messages`' upload-queue pattern for local calendar writes awaiting sync. `get_calendar_events_in_range` returns a recurring event's row regardless of whether its own master `dtstart_utc`/`dtend_utc` overlaps the query window (a later occurrence can still fall inside it) — expanding to individual occurrences is `calendar::expand_occurrences`/`calapp::expand_recurring_events`'s job, not this query's
- **sync.rs** — `jamaild`-internal per-account sync thread lifecycle: SyncControl (current_folder, folder_filter, mark_seen_queue, `flag_queue` + `recently_flagged` (stars, same shape as mark-seen: newest choice per message wins, the local choice overrides a stale server answer for ten minutes), upload_queue, `force_sync`, and `recently_seen`, the set of messages the user just read in jamail), multi-folder sync loop, SyncEvent enum (includes UploadComplete/UploadError for Sent/Draft folder APPENDs). Each pass runs **queued actions first** (`apply_pending_actions`: `\Seen` stores — re-queued up to `MARK_SEEN_MAX_ATTEMPTS` when the server rejects them — then Sent/Draft uploads), then every folder's new mail, then flags for the folder on screen (every folder every `FULL_FLAG_SYNC_INTERVAL`), then IDLEs on the current folder in `IDLE_CHUNK` rounds (10 s) for `IDLE_PHASE` (60 s): a queued action, a `SyncNow`, new mail in the current folder, or an IDLE error (dead socket) ends the round at once. Connection attempts back off 5 s → 60 s. `SyncControl.last_progress` is touched at every round, pass and fetch batch, and `abort_connection()` cuts the live socket: the daemon's housekeeping thread checks every 10 s and cuts a connection silent for `STALL_TIMEOUT` (5 min), `ForceReconnect` cuts it at once, and every `SyncEvent::Error` is logged to stderr (the journal) so an unattended daemon's trouble is visible. Unchanged in shape from before the daemon split — `daemon.rs` now owns one instance of this per account instead of `jamail`'s old main.rs owning a single one for whichever account was active. `UploadKind` also derives `Serialize`/`Deserialize` — reused verbatim as the wire type in `ipc::Request::EnqueueUpload`/`ipc::Event::UploadComplete`/`UploadError`
- **config.rs** — YAML config deserialization (JamailConfig, JamailAccount, ImapConfig, AuthConfig, SmtpConfig). `JamailAccount` also carries `senders` (multiple From identities), `sent_folder`/`draft_folder` (remote upload destinations, each independently `Option<String>` — unset disables upload), `notify_folders` (desktop-notification trigger folders), and `show_unlisted_folders` (bool, default `false` — when `folders` is set, also sync/show remote folders not listed there) — all optional and backward-compatible. `JamailConfig.daemon: Option<DaemonConfig>` (optional `socket_path` override) is read independently by both binaries. `CalDavConfig` carries `auth: Option<AuthConfig>` **and** `oauth: Option<CalDavOauthConfig>` (`provider` (only `google`), `client_id`, `client_secret`, and `refresh_token: Option<AuthConfig>` — optional purely so the documented bootstrap order works: configure the client, run `jamaild google-auth`, then name the token it wrote); `CalDavConfig::check()` rejects a block naming neither. `JamailConfig.jacal: Option<JacalConfig>` carries `week_start` and `calendars: Vec<JacalCalendarPref { url, visible, color }>`, the per-calendar display settings `jacal` writes back itself through `save_jacal_calendar_prefs` → `splice_jacal_calendars`: a pure, line-based rewrite of exactly the `jacal.calendars` list (inserted into the existing `jacal:` block, or a new block appended) that leaves every other byte of the file — comments, quoting, credentials — untouched, is parsed back and compared before writing, and lands via a same-permission temp file plus rename
- **smtp.rs** — SMTP email sending via `lettre` (blocking transport, STARTTLS/implicit TLS, plain text and multipart with attachments); stays entirely client-side (`jamail`'s `SendQueue`) since sending is a synchronous foreground action tied to the compose UI. `send_email` returns the raw sent bytes for Sent-folder upload; `build_draft_raw` builds a tolerant (empty-recipients-OK) raw message for Draft-folder upload. `SendJob`/`SendResult` carry `account` (captured at enqueue time) so a Sent-folder upload always targets the account the message was actually sent from, even if the user switches accounts in the UI before the background send completes
- **notify.rs** — Best-effort desktop notification (`notify-send`) + sound (`canberra-gtk-play`/`paplay`/`pw-play`, tried in order) for accounts with `notify_folders` configured; no-ops silently when the tools aren't installed, same pattern as clipboard copy. Called exclusively from `daemon.rs` (`dispatch_sync_event`/`default_notifier`) — `jamail` (the client) never references this module
- **theme.rs** — Color palette and style constants (dark theme, all RGB values, compose view colors, Sent/Draft status badge colors)
- **thread.rs** — Email threading via Message-ID/In-Reply-To/References + subject-based fallback; caches `newest_status_label` from the newest email, `has_attachments` and `has_flagged` (any starred message) for thread-summary row rendering
- **calendar.rs** — iCalendar (RFC 5545) `VEVENT` domain model, parser, and serializer. Standards-conscious subset: parses UID/DTSTART/DTEND/SUMMARY/DESCRIPTION/LOCATION/STATUS/ORGANIZER/ATTENDEE/RRULE/EXDATE/VALARM, timezone-aware via `chrono-tz` (IANA names only — a non-IANA `TZID` is an explicit `CalendarError::UnsupportedTimezone`, not a silent misparse). `expand_occurrences` (backed by the `rrule` crate, expanding in the event's own `TZID` zone so a 16:00 Berlin weekly stays at 16:00 across the DST change) computes every occurrence of a recurring event overlapping a window, honoring `EXDATE`; `expand_document_occurrences` does it for a whole stored document and applies its `RECURRENCE-ID` overrides the way RFC 5545 means them — a moved instance appears on its new day only, a `CANCELLED` override removes the slot — which is what `jacal`'s display and `jamaild`'s alarm clock both use; for display purposes only — editing/deleting a recurring event always acts on the single master `VEVENT`; `RDATE`/`EXRULE` are preserved for round-tripping but not expanded. Edits patch the original raw `VEVENT` text in place (`VEvent::to_ics`) so properties this module doesn't model (`CATEGORIES`, `X-` extensions, etc.) survive unchanged — and only a value that actually differs counts as a change, so re-saving an untouched form never bumps `SEQUENCE` (which would make the server re-invite everyone). `EventEdits.alarms` (minutes before start → `DISPLAY` `VALARM`s, `parse_alarm_list`/`format_alarm_short`/`describe_alarm`) and `EventEdits.attendees` + `organizer` (kept guests keep their line and `PARTSTAT`, new ones get `NEEDS-ACTION;RSVP=TRUE`, missing ones go) are re-rendered wholesale from the model through a `PatchScope`, everything else stays verbatim, and neither touches `SEQUENCE`; `patch_document` splices that patched block back into the event's original `VCALENDAR` document (matching the series master by `UID` and absence of `RECURRENCE-ID`, see `is_recurrence_override`), so the wrapper, `PRODID`, `VTIMEZONE` blocks and override components survive too and the result is always a complete object a strict server accepts — `db::apply_local_calendar_edit` goes through it, never through `to_ics` alone. `RRULE` is in `PROPERTY_NAMES_TO_PATCH` so a recurring event's rule is dropped and re-emitted exactly once per edit
- **goauth.rs** — Google OAuth 2.0 (installed/"Desktop app" client, PKCE S256), the one implementation shared by `jamaild`'s CalDAV sync and `jadav`'s Google mirror: `build_auth_url`/`parse_redirect`/`exchange_code`/`authorize_interactive` (the browser round trip, redirect pasted back — no loopback listener), `refresh_access_token` (whose `TokenError::{InvalidGrant, Transport, Other}` split is what lets `jadav` map a revoked token to `RemoteError::NeedsReauth` and `calsync` retry a 5xx), and `GoogleTokenSource`, a `caldav::TokenSource` caching the access token in memory until a minute before expiry. Stores no refresh token itself — `jamaild` reads one from config, `jadav` from its store — except through `write_refresh_token`, which `jamaild google-auth` uses to park one in a `0600` file so the secret never reaches the terminal's scrollback. `caldav_url_for` builds Google's documented CalDAV principal URL (`.../caldav/v2/<address>/user`)
- **httpc.rs** — Minimal synchronous HTTP/1.1 client (arbitrary methods, headers, redirects, chunked/content-length bodies) built directly on `native_tls`/`std::net` rather than a new HTTP client dependency, used only by `caldav.rs`
- **caldav.rs** — Synchronous CalDAV (RFC 4791) client. Authenticates as `AuthScheme::Basic` or `AuthScheme::Bearer(Arc<Mutex<dyn TokenSource>>)` (a `401` on the bearer path invalidates the token and retries the request exactly once with a fresh one); the enum is `Clone` so one scheme outlives the per-cycle client, and its `Debug` is hand-written to never render the credential. RFC 4791 discovery (`current-user-principal` -> `calendar-home-set`), RFC 6578 `sync-collection` change sync with `calendar-query` full-listing fallback, and `GET`/`PUT`/`DELETE` with `If-Match`/`If-None-Match` ETag conflict protection. Discovery also asks for Apple's `calendar-color` and jadav's `owner-identity` (`DiscoveredCalendar.color`/`.identity`), which `calsync` stores through `db::upsert_calendar_with_color` (a `None` never erases a stored value) so `jacal` can default to the colour the server — jadav seeding Google's — gave the calendar and knows which identity organises events created there. WebDAV multistatus XML parsed via `quick-xml` — note quick-xml ≥ 0.38 delivers entity/character references (`&quot;`, `&amp;`, `&#38;`…) as separate `GeneralRef` events, which `parse_multistatus` resolves via `general_ref_text`; servers escape the quotes around ETags this way, so dropping them would store unquoted ETags and break every `If-Match`. Tested against a local mock HTTP server whose fixtures use the escaped forms (see module doc for the TLS-untested scope limitation, mirroring `tests/smoke.rs`'s IMAP one)
- **calsync.rs** — `jamaild`-internal per-account CalDAV sync thread (`CalSyncControl`, poll loop since CalDAV has no IDLE equivalent — interval from `config::CalDavConfig::poll_interval_secs`), applying outstanding local writes before each sync pass. `resolve_auth`/`connect` turn one `caldav:` block into a client: a Basic password is re-resolved every cycle (a rotated `type: command` secret needs no restart), while an OAuth token source is built once per thread and cached in the loop's own `Option<AuthScheme>` — it *is* the access-token cache, so rebuilding it per cycle would spend a refresh call every poll interval instead of one an hour. The `CalMutation` write queue is only a wake-up hint (`enqueue` sets `force_sync`); the work list is every row still in a `pending_*` state, and `apply_pending_write` dispatches on that status rather than on the queued variant. ### Key Design Decisions

- **Email bodies are zstd-compressed** (level 3) in the database. Only decompressed when opening detail view. Preview text (first 200 chars) is stored uncompressed for list rendering.
- **Emails have an autoincrement `id`** (PK) separate from IMAP `uid`. UID is only unique within (account, folder). All UI lookups use `id`.
- **FTS5 is a standalone table** (no `content=` directive) — stores its own inverted index. FTS rowid = emails.id.
- **Database schema versioning** — `schema_version` table tracks version. On upgrade, all tables are dropped and recreated (DB is just a cache).
- **IMAP sync is incremental** — tracks UIDVALIDITY and last_uid per (account, folder) in sync_state table.
- **`BODY.PEEK[]`** is used instead of `BODY[]` to avoid marking messages as \Seen on the server.
- **Auth supports `password` and `command` types** — command runs a shell command and captures stdout (e.g., `pass show email/work`). Reused for both IMAP and SMTP.
- **SMTP is optional** — `SmtpConfig` is an `Option` on `JamailAccount`. Compose/reply/forward UI is always available; sending shows an error if SMTP is not configured. Uses `lettre` crate with blocking transport (no async runtime).
- **Compose state lives on `App`** — all compose fields (to, cc, bcc, subject, body lines, cursor position, attachments, autocomplete, file browser) are flat fields on the `App` struct. `ComposeField` enum tracks which field is active; `ComposeMode` tracks New/Reply/Forward.
- **Body editor operates on `Vec<String>`** — one element per line, with `(cursor_row, cursor_col)` in char units. `char_to_byte_pos()` converts char index to byte offset for correct string manipulation.
- **Contact autocomplete** — `db.get_known_addresses()` extracts distinct from/to addresses from the cache. Filtered by substring match on the current token (text after last comma) in address fields. Up to 10 suggestions shown as an overlay.
- **Forward auto-attaches originals** — attachment data is extracted from DB, written to `/tmp/jamail_fwd_<id>/`, and added to `compose_attachments`. Temp files are cleaned up on send or cancel.
- **Date parsing** uses `mailparse::dateparse` as primary parser, with a custom `normalize_timezone()` preprocessing step that maps non-RFC2822 timezone abbreviations (CEST, BST, JST, etc.) to numeric offsets before parsing.
- **Mouse selection** is constrained to the detail panel's inner rect (`selectable_area`). Text is extracted from ratatui's `CompletedFrame` buffer on mouse release and copied via wl-copy/xclip/xsel.
- **Threads store indices, not clones** — `Thread.email_indices: Vec<usize>` references into `App.emails`. Summary data (`newest_from`, `has_attachments`) is cached on the Thread struct to avoid lookups during rendering. `build_threads()` takes `&[Email]`.
- **Parallel email processing** — `sync_folder` uses `std::thread::scope` to run `process_raw_email` calls concurrently (w3m subprocesses). Capped at `PROCESS_PARALLELISM` (8) concurrent threads per sub-batch to limit peak memory from attachment data.
- **SQLite memory limits** — `PRAGMA cache_size = -4000` (4MB cap per connection), `PRAGMA mmap_size = 0` (no memory-mapped I/O).
- **Multiple sender identities** — `accounts.<name>.senders` (optional) lists "From" identities cycled via Left/Right on the compose From field. `App.compose_senders` is always rebuilt from config at compose-entry time, so the From field can only ever hold a configured value; `compose_from_is_valid()` re-checks this immediately before a send is enqueued.
- **Folder display order matches sync order** — `mail::order_folders()` is the single source of truth for both what each account's sync thread in `jamaild` syncs (`SyncControl.folder_filter`) and what `jamail`'s folder selector shows (`App.rebuild_folder_tree`, driven by `ipc::Event::FoldersLoaded`), keyed off the same `accounts.<name>.folders` config. Unconfigured: INBOX first, then alphabetical (deterministic default, since IMAP LIST order and DB-cache order aren't guaranteed to agree or stay stable). When `folders` is set, `accounts.<name>.show_unlisted_folders` (default `false`) controls whether remote folders absent from that list are appended after it (same INBOX-first/alphabetical order) instead of being hidden/unsynced entirely.
- **Folder-selection cursor survives tree rebuilds** — `App.rebuild_folder_tree()` captures the currently-selected row's identity (account+folder name, or the virtual/global-inbox/account sentinel) before rebuilding, then relocates the cursor to that same row afterward regardless of index shifts from reordering, expand/collapse, or newly-synced folders; falls back to the first row when that identity is no longer present (row removed, account collapsed). `App.enter_folder_select()` relies on this instead of resetting the cursor, so reopening the folder selector returns to where you left it.
- **Remote Sent/Draft folder upload is opt-in and one-shot** — `sent_folder`/`draft_folder` are independent `Option<String>` keys; unset means "local cache only" (no APPEND attempted). A sent message is uploaded once (after a successful SMTP send); a draft is uploaded once, on its *first* explicit `Ctrl+S` save only — later edits update the local cache but do not re-upload, so there's no remote delete/replace-on-update logic to track a remote UID. `jamail` sends the raw message (base64'd) to `jamaild` as `ipc::Request::EnqueueUpload`, which pushes onto that account's `SyncControl.upload_queue`, drained by its sync thread (which already owns a live IMAP connection) alongside `mark_seen_queue`; results come back as `ipc::Event::UploadComplete`/`UploadError`.
- **Sent/Draft in-flight state never disappears silently** — `local_messages.status` includes `sending` and `send_error` (not just `draft`/`sent`), and `get_drafts()` includes all three non-`sent` states so a message stays visible (with a "Sending…"/"Send failed: ..." badge) through the whole send lifecycle. `upload_status`/`upload_error` track the independent Sent/Draft-folder upload outcome the same way. `Email.status_label` (set only for local Drafts/Sent rows) carries the badge text into both the flat and threaded list renderers.
- **Stars are IMAP `\Flagged`, and the star follows the message everywhere** — `*` (or `S`) in the list or the detail view flips `emails.is_flagged` in the cache and every loaded row at once (`App::toggle_star`), then sends `ipc::Request::SetFlagged`; the daemon queues the `\Flagged` store like a mark-seen (applied at the start of the next pass, within one IDLE round, re-queued on a rejected store) and shields the local choice from a stale server answer for ten minutes. Sync reads `\Flagged` off every fetched message and every flag pass, so a star set on the phone shows up here as `★` in the list rows (yellow, between the unread dot and the attachment mark; a thread row shows it when any message in the thread is starred) and before the subject in the detail header. Local Drafts/Sent rows cannot be starred.
- **A message read in jamail never flips back to unread on its own** — jamail marks it read locally and queues `MarkSeen`; the daemon records it in `SyncControl.recently_seen`, applies the `\Seen` store *before* the flag sync of the pass (and within one 10-second IDLE round of the request), re-queues a rejected store, and `MailClient::sync_flags` ignores a stale "unseen" from the server for anything read locally in the last ten minutes. The old order (flags before stores, stores dropped on error) is what made the unread dot come back.
- **A dead IMAP connection is detected, never waited on** — three independent layers, because the failure that motivated them (a suspend left the socket established locally with the peer gone, and the sync thread sat in a read for 20 hours with no error anywhere) defeats any single one: TCP keepalive makes the kernel fail the blocked read within about a minute of the peer vanishing; a socket-level read timeout bounds every read the `imap` crate performs without one (re-applied after each IDLE round, since the crate clears it); and the daemon's stall watchdog cuts the socket from outside when the loop shows no progress for `STALL_TIMEOUT`, as does `ForceReconnect` on a detected wake. Sync errors go to the journal, not only to a connected client.
- **Desktop notifications are owned entirely by `jamaild`** — `notify_folders` (optional, per account) lists folders that trigger a `notify-send` desktop notification + best-effort sound (`canberra-gtk-play`/`paplay`/`pw-play`) on new mail, mirroring the existing external-tool-with-graceful-fallback pattern (w3m, xdg-open, wl-copy/xclip/xsel). Unset means no notifications. The decision and the call both happen in `daemon::dispatch_sync_event`, run from each account's event-pump thread inside `jamaild` — never in `jamail`, and never gated on any client being connected, which is what makes this work under `systemd --user` with no terminal open at all. Fires once per `FolderComplete` sync event (not per message), so an initial full backfill sync produces one notification with the total count rather than one per message.

- **Google Calendar is reachable from `jamaild` itself, and its credential is a refresh token in the config** — Google's CalDAV endpoint takes no password of any kind (not even an App Password), so `caldav.oauth` replaces `caldav.auth` for such an account and `caldav.rs`'s `AuthScheme::Bearer` carries the token. The one interactive step is `jamaild google-auth <account>`: it reads the OAuth client out of the account's own config, runs the PKCE flow in `goauth.rs`, and writes the refresh token to a `0600` file whose `cat` the user names as an ordinary `type: command` secret (`--print` hands it over instead, for `pass`) — the daemon then needs no browser, no token database, and no new state beyond what config already holds. Access tokens live in memory in a token source built **once per sync thread**, since that source is the cache: a per-cycle one would spend a refresh every poll interval. A revoked or expired refresh token (`invalid_grant` — the everyday outcome of leaving the OAuth client in Google's *Testing* publishing status, which expires them after 7 days) is surfaced and logged, never retried into a rate limit, because only a human at a browser can fix it. This puts nothing of `jadav` in the mail client's path: the two share `goauth.rs`, not a store, and an account can use either or both.
- **Answering an invitation in `jacal` is a `PARTSTAT`-only edit, and the server does the talking** — `r` opens `CalMode::Rsvp` for the selected event (refused with a reason when none of our identities is on the guest list, or when we are the organizer), and accept/tentative/decline becomes `EventEdits { rsvp: Some(Rsvp { attendee, partstat }) }` applied through the same `apply_local_calendar_edit` → `CalMutation::Update` path an edit uses. `calendar::apply_rsvp` rewrites exactly our `ATTENDEE` line (dropping `RSVP=`, keeping every other parameter) and never bumps `SEQUENCE`, because the sequence number is the organizer's. jacal sends no mail: the CalDAV server (jadav, or any RFC 6638 server) sees the changed `PARTSTAT` on PUT and emits the iTIP `REPLY` — which is also why an RSVP to a read-only mirror surfaces as an ordinary sync error rather than needing client-side knowledge of which calendars are answerable.
- **A calendar's look is the user's, and it lives in `config.yaml`** — `jacal.calendars` records, per calendar URL, whether it is shown and which colour the user picked; `jacal` reads it at startup and writes it back on every toggle (`1-9`, or the `C` panel) and colour change. The write is a textual splice of that one list (`config::splice_jacal_calendars`), never a re-serialisation of the whole document: the file holds credentials and hand-written comments, and a round-trip through serde would drop the comments and re-quote everything. The rewritten text is parsed back and compared before it replaces the file. Colour precedence is user → server (`calendar-color`, which jadav seeds from Google) → palette by position.
- **The current time is a red band, the selection is yellow text and border marks** — today's column paints the slot the clock falls in with `NOW_BG` edge to edge when no event touches it; inside an event's rows the event keeps its tint and the clock is red under its own characters only — `now_label_position` puts `NOW hh:mm` at the left edge when that is free, else right after the running event's bar (its "empty" lines carry the clock), else on the neighbouring row when a title starts on the slot. The selected event keeps its calendar tint too (no separate selection background): its text turns bold `SELECTED_FG` and `mark_selected_row` writes `>`/`<` into the column's border cells on that row (columns and Month cells; the line builders return the selected line's index for it). 
- **Event rows say whose calendar and what we answered** — the row background is the calendar colour tinted into the cell background (`EVENT_TINT_PERCENT`) across the full column width, including the slots a long event runs through, and the marker glyph is our own participation: `●` going (or plain event), `○` maybe, `◦` not answered, `✕` declined/cancelled (struck through). Participation is computed once per load from the `ATTENDEE`/`ORGANIZER` lines against `CalApp.identities`, so mirrored Google events show the same Going/Maybe/Can't go the phone does.
- **`mirror_all` follows the account, config follows the calendar** — a Google remote with `mirror_all: true` gets every calendar on its calendar list mirrored under `<slug_prefix>-<slugified name>` (default prefix `g-<remote>`, so a slug always says which account it came from), display name `<name> (<remote>)`, read-write only where Google grants owner/writer access, free/busy-only entries never; explicitly configured calendars keep their own slug and settings, and `skip_calendars` excludes by name or id. Discovered calendars are marked `discovered` in the store so config reconciliation never nags about them, are re-listed hourly by the remote's mirror thread, and are mirrored again straight after a restart from the store. A calendar removed on Google stops updating but is never deleted locally.
- **`Esc` in `jacal` is "go back", never "quit"** — `CalApp` keeps a `view_history` of `ViewPosition`s (view + anchor + focused day + event cursor), pushed by `narrow_view`/`widen_view`/`zoom_in`. `go_back` pops one and restores the *whole* position, so `Enter`ing a day out of Month view and pressing `Esc` returns to that month on the same cell rather than to 3-Day (which is what a plain "one step wider" would give). With an empty history it returns `false` and `jacal` says so in the status line; `q` is the only key that exits.
- **Calendar views narrow and widen, they don't cycle** — `CalView` is declared widest-first (`Year, Month, Week, ThreeDay, Day, Event`); `CalView::narrower`/`wider` are saturating (`Option`), so `Tab` always steps into a smaller range and `Shift+Tab` into a larger one, neither wrapping around. `CalApp::switch_view` re-anchors the visible period on the *focused day* (so Week -> Day lands on the day you were looking at) and preserves `event_cursor` between two columnar views, which is what makes `Day -> Event` open the event under the cursor — and `zoom_in` (Enter) from Week or 3-Day goes straight to that event when one is selected, narrowing to the day only when nothing is. Note `jacal` must match bare `KeyCode::BackTab` as "widen": most terminals report Shift+Tab as `BackTab` **without** `KeyModifiers::SHIFT`.
- **One shared time axis per group of equal-height columns** — `calapp::plan_time_axis` builds a single `TimeAxis` from every displayed day's timed events, so 09:00 lands on the same terminal row in every column and days are comparable by eye. Week view (`week_columns`) puts Saturday and Sunday stacked into the last column (chronological within the displayed week); those half-height columns share an axis of their own (`plan_group_axis`), the weekdays share theirs. It shows exactly `DAY_CORE` (07:00-21:00) stretched only as far as an event on *any* displayed day requires (`render_columns` hands every group the spans of all visible days, so early or late events extend every column alike), and picks the finest slot from `SLOT_CHOICES` (5, 10, 12, 15, 20, 30, 60… minutes — every choice divides the hour, so the ruler still lands on whole hours) that fits that range in the rows available; leftover rows stay blank rather than showing extra hours, so a taller terminal buys a finer slot, never a longer day. It returns `None` below `MIN_GRID_ROWS`, and `render_columns` also skips the grid below `MIN_GRID_COL_WIDTH` — either way falling back to the pre-existing stacked `cell_event_lines` list. All-day events have no place on a time axis, so they get banner rows above it, a uniform number across every column so the grids stay aligned. An empty slot shows only the hour (`09h`, blank on the rows between), or `now` on today's current slot — enough to read the ruler by without turning the column into a wall of timestamps.
- **Overlapping events cascade; the column is never divided** — a day column's width always belongs to one event at a time, so every title is readable. `calapp::pack_cascade` (pure, unit-tested) gives each of a day's timed events a `(start_row, indent)` from two rules: **one event begins per row** (a clash slides down to the next free line) and **an event indents one column deeper than everything it overlaps in time**, capped at `width / CASCADE_INDENT_SHARE`. Rendering draws the owner's line from its indent to the full width, and the continuation bars of the events it is nested under in the columns to its left — anything at or past the owner's indent is deliberately left undrawn, since covering it is the point. A row's ruler label is only drawn when nothing has claimed the left edge. An event the cascade slid off its own slot always prints its real start time (`CellText::WithTime`, even in a column too narrow for one), so a stacked clash never claims the wrong time.
- **One glyph for "an event": `EVENT_DOT` (`●`)** — the bullet on an event line in the columnar views, and the *entire* representation of an event in Month cells (a dot strip, the one line that survives in a 1-row-tall cell on an 80x24 terminal) and Year mini-months (one dot per day, with the dot column reserved even on empty days so the day numbers stay aligned). Color carries the meaning: `CalApp::event_dot_color` gives each calendar its stable `theme::ACCOUNT_COLORS` entry, overridden to red for an unresolved sync conflict.
- **Deleting an event is decided once, up front** — `CalApp::begin_delete_confirm` captures a `PendingDelete { id, summary, recurring }` instead of re-reading the cursor at confirm time, because `jacal`'s event loop keeps reloading (and re-sorting) events while the prompt is on screen. `db::mark_calendar_event_pending_delete` returns whether a remote `DELETE` is still owed: a never-uploaded row is removed outright and the caller must **not** queue a mutation for its id, since SQLite reuses rowids. `get_calendar_events_in_range` excludes `pending_delete` rows so a deleted event leaves the UI (and stops firing alarms) immediately, and `upsert_calendar_event` preserves that status so a read pass arriving before the `DELETE` lands can't resurrect the row.
- **The calendar write queue is a hint; the database is the work list** — `calsync::run_one_cycle` drains `CalSyncControl::write_queue` (which `enqueue` now pairs with `force_sync`, so a create/edit/delete reaches the server in under a second instead of at the end of a 5-minute poll) and then picks up every row the database still has in a `pending_*` state, so a write queued before `jamaild` restarted or one whose last attempt failed is retried rather than lost. `calsync::apply_pending_write` dispatches on the **row's own `local_status`**, never on the queued `CalMutation` variant — a stale queue entry naming a reused rowid must not delete a different event. Two namespaces short-circuit the network entirely: a row still carrying `db::LOCAL_HREF_PREFIX` (`local:`) was never uploaded, and a calendar under `db::SERVER_CALENDAR_URL_PREFIX` (`server:`) is hosted by this daemon (`db::server_commit_local_write` commits it locally and appends the `calendar_sync_log` entry subscribed clients read). For the same reason `prune_calendars_not_in` never prunes `server:` calendars — `keep_urls` comes purely from remote discovery, so they could never appear in it.

- **jadav is a server with its own store, not a fourth client of `mail.db`** — the cache's tables are keyed by remote URL with one `server:`-namespaced calendar per account, while jadav owns many calendars per principal with providers, identities, write origins, an append-only change log and (later) mirror/scheduling bookkeeping. Config owns a calendar's *facts* (identity, provider, remote, two_way, send_via, default flag) on every start; CalDAV clients own its *presentation* (name, colour, description, order, timezone) after first creation. Every object write records an `Origin`; only `Client` writes will ever trigger scheduling, only non-`Mirror` writes are pushed to remotes, and a client delete on a mirrored calendar is a soft delete (tombstoned for clients at once, kept for the mirror to push). Sync tokens are `urn:jadav:<slug>:<change_log id>`; compaction moves `sync_baseline_id` up so a too-old token is refused with `valid-sync-token` instead of being answered incompletely, and `AUTOINCREMENT` ids plus `sqlite_sequence` mean a recreated slug can never accept its predecessor's tokens. Objects whose `TZID` this crate cannot resolve are stored *unindexed* (always returned by `time-range`) rather than rejected — a server must round-trip Outlook's Windows zone names.
- **jadav is the scheduling agent, and mail is its transport** — a client's PUT/DELETE is the only thing that ever produces an iTIP message (`Origin::Client`); mirror and inbound-mail writes *are* the other side's message and never echo one. Messages are queued in the same SQLite transaction as the object they belong to and sent later by the outbound worker, so a crash between the two is impossible and an SMTP outage only delays. Every message goes out through the operator's own SMTP server `From:` the calendar's identity with no `Sender:` header, because that server's sender-dependent relay (each identity out through its own provider) is what keeps SPF/DKIM/DMARC aligned; `send_via: provider` per calendar is the escape hatch that leaves scheduling to Google instead. Inbound mail is routed by the ICS `ATTENDEE`/`ORGANIZER` lines (a fetcher's `acct-*` keyword only breaks ties), applied once per Message-ID no matter how many folders it passes through, and never flagged, moved or deleted. A CANCEL sets `STATUS:CANCELLED` rather than deleting, because a client-side delete of an attended event is itself a DECLINE. Invitations for a *mirrored* calendar are not applied from mail at all: the provider already has them, the mirror brings them, and applying them here would push a duplicate back.
